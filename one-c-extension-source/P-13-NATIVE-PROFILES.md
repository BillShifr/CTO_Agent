# P-13: автоматическое создание нативных профилей

Инструкция только для стороны 1С:
[P-13-ONE-C-PRODUCTION.md](P-13-ONE-C-PRODUCTION.md). Полная инструкция с агентом:
[P-13-PRODUCTION-INSTALL.md](P-13-PRODUCTION-INSTALL.md). Инструкции не подтверждают

Выгрузка подтверждает структуру и примеры данных, но не выполнение кода 1С. Клиентские
данные, номера счетов и GUID из выгрузки не включены в исходники. Полная цепочка с возвратом
не найдена; штатная процедура печати из OData не извлекается.

## Блок специалиста 1С

Добавить в проект расширения общий модуль `AvtoPultНастройкаПрофилей`: серверный,
неглобальный, непривилегированный, без вызова сервера из клиента. Код — в
`src/CommonModules/AvtoPultНастройкаПрофилей/Module.bsl`.
Модуль включён в manifest сборки и самопроверку установки. Новых регистров и HTTP-маршрутов нет.
Запускать на сервере 1С с правами чтения исходных документов/справочников/регистров движений,
создания заказа и записи двух регистров профилей. Права не повышаются программно.

Для всех станций и профилей проведения можно выполнить один вызов. Сначала модуль
разрешает и проверяет все ссылки, затем создаёт профили. Повтор безопасен:

```bsl
JSONНастроек = "{""stations"":[{""stationId"":""STATION-ID"",""orderNumber"":""ORDER-NUMBER"",""year"":2026,""lineNumber"":1}],""postingProfiles"":[{""profileId"":""cash-receipt-v1"",""documentType"":""ПриходныйКассовыйОрдер"",""documentNumber"":""CASH-DOCUMENT-NUMBER"",""year"":2026}]}";
Результат = AvtoPultНастройкаПрофилей.НастроитьПрофилиИзJSON(JSONНастроек);
```

Если какой-либо профиль не успел создаться из-за ошибки последующего профиля, после
исправления JSON выполнить тот же вызов: уже созданные записи вернут `replayed`, дубли
не появятся.

### Создать профиль СТО

Вместо создания образца и ручного заполнения `AvtoPultПрофилиСтанций` выполнить:

```bsl
Результат = AvtoPultНастройкаПрофилей.СоздатьПрофильСтанции(
    StationId, ЗаказИсточник, НомерСтроки);
```

Входные значения:

Ссылку на документ можно получить без GUID:

```bsl
ЗаказИсточник = AvtoPultНастройкаПрофилей.НайтиДокумент(
    "ЗаказКлиента", "НОМЕР-ИЗ-1С", 2026);
```

Тип проверяется по разрешённому списку. Номер и год задаются по документу текущей базы;
при отсутствии документа или нескольких совпадениях функция останавливается.

- `StationId` — идентификатор станции из СТО, строка.
- `ЗаказИсточник` — ссылка на выбранный заказ клиента **текущей базы** с нужными
  организацией, подразделением, соглашением, валютой и складом. Проведённый источник допустим.
- `НомерСтроки` — номер выбранной строки товаров, начиная с 1. Строка не отменена,
  сумма НДС нулевая, номенклатура, ставка НДС и вид цены заполнены.

Создаётся отдельный непроведённый технический заказ: одна строка, количество 1,
нулевые цена и суммы. Источник не изменяется. Настройки шапки и строки копируются по
явному списку; клиентские платежи, счета и движения не копируются. Профиль получает ссылку
на технический образец. Сохранённые значения перечитываются; изменения значений обработчиками
или неожиданные движения отменяют транзакцию вместе с созданием профиля.

Результат содержит `status` (`created` / `replayed`), `template` (ссылка), `verified`.
Повтор с совпадающими настройками не создаёт документов и сохраняет флаги приёмки.
Другие настройки под тем же StationId дают `PROFILE_SETTINGS_CONFLICT`, существующий профиль
не перезаписывается. Если технический образец изменён/проведён, повтор отклоняется.

`Проверен` и `БезНДСПодтверждено` при создании ложны. Нулевая сумма НДС в одной строке
не доказывает правильность налогового режима. Флаги включаются после нативной проверки.
Разные склады/виды цен в строках и поддержка НДС адаптером этой функцией не добавляются.

### Создать профиль проведения

Вместо ручного копирования типа, массива регистров и хеша выполнить:

```bsl
Результат = AvtoPultНастройкаПрофилей.СоздатьПрофильПроведения(
    PostingProfileId, ДокументИсточник);
```

`PostingProfileId` — согласованное имя профиля, например `cash-receipt-v1`.
`ДокументИсточник` — ссылка на существующий проведённый документ нужного типа и операции
в текущей базе. Скрипт читает его движения через `СформироватьПрофильДвижений`, затем
атомарно записывает `ТипДокумента`, `РегистрыJSON`, `SHA256`. Пустой результат или ошибка
чтения регистра прерывают создание. Документ не перепроводится.

Совпадающий повтор возвращает `replayed`; расхождение типа/регистров/хеша —
`PROFILE_SETTINGS_CONFLICT`. Проверенный профиль никогда не сбрасывается повторным запуском.
Новый профиль остаётся `Проверен = Ложь`, дата приёмки не заполняется.
Сборщик сейчас исследует регистры накопления; бухгалтерские и информационные регистры
этим результатом не сертифицируются. Один документ не доказывает все варианты движений типа.

## Обязательные проверки внутри 1С

1. Создание из проведённого источника: источник и его движения неизменны; новый образец
   непроведённый, с одной нулевой строкой. Оба флага проверки ложны.
2. Повтор и два одновременных запуска для одного StationId: один образец, одна запись профиля.
3. Другой склад/вид цены под существующим StationId: ошибка; старые настройки сохранены.
4. Ошибка обработчика записи/нехватка прав чтения движений: нет нового образца и профиля.
5. Отменённая строка, удалённый справочник, НДС, неверный номер строки: создание отклоняется.
6. Профиль проведения: совпадающий повтор не меняет флаги; другой набор движений отклоняется.
7. Нативная приёмка проведения и полного отката по `POSTING-METADATA.md`.

Статические проверки исходников не заменяют эти сценарии. Боевая инструкция использует
результат подготовленного и проверенного расширения; сборка и испытания выполняются заранее.
