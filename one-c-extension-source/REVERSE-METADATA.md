# Журнал обратных изменений — FR-INT-006

Реализован исходник записи ревизий, **не завершён обратный обмен**. Нативная компиляция
и запуск не подтверждены. Не устанавливать в production до проверки на копии.

## Метаданные расширения

- Серверный неглобальный непривилегированный модуль `AvtoPultИзмененияЗаказов`.
- Подписка на событие `ПриЗаписи` объекта `ДокументОбъект.ЗаказКлиента`:
  обработчик `AvtoPultИзмененияЗаказов.ПриЗаписиЗаказа(Источник, Отказ)`.
  Не использовать событие формы: программные записи также должны фиксироваться.
- Независимые непериодические регистры с управляемыми блокировками:
  - `AvtoPultГоловыИзмененийЗаказов`: измерение `WorkOrderId` (строка 128);
    ресурсы `Sequence` (число 15,0), `RevisionId` (строка 36).
  - `AvtoPultИзмененияЗаказов`: измерения `WorkOrderId` (строка 128), `Sequence` (число 15,0);
    ресурсы `RevisionId`, `ParentRevisionId` (строки 36), `ЗаказКлиента`
    (ДокументСсылка.ЗаказКлиента), `BaseVersion` (число 10,0), `BasePayloadJSON`,
    `PayloadJSON` (неограниченные строки), `SHA256` (строка 64),
    `СозданоВ` (дата со временем, UTC), `Состояние` (строка 32),
    `Origin` (строка 16), `CommandVersion` (число 10,0),
    `AcceptedCloudPayloadJSON` (неограниченная строка),
    `AcceptedCloudPayloadSHA256` (строка 64).

Обработчик читает только уже связанные заказы. В одной транзакции с документом сохраняет
новую ревизию и ссылку на неё; старые снимки не перезаписываются. Два изменения в секунду
различаются последовательностью, а не временем. Ошибка записи журнала не проглатывается.
Запретить пользователям ручное изменение/удаление журнала и голов, ограничить чтение:
исходный снимок AvtoPult может содержать клиентские данные.

## Что снимок означает

Это внутренние данные 1С, не `workorder.changed`. Денежные поля снимка — числа в валюте
документа, **не тиыны**. `nativeStatus` — диагностическое представление, не команда перехода.
`lineCode` — нативный `КодСтроки`, не индекс массива и не `itemId` AvtoPult.
Исходный `BasePayloadJSON` сохраняет известные стабильные ID и правила строк на момент записи.
Снимок не подтверждает результат проведения или движения регистров: `ПриЗаписи` выполняется
внутри транзакции и может предшествовать обработке проведения. Порядок описан в
[документации платформы](https://1c-dn.com/library/document_sequences/).

## Следующий обязательный шаг

Пока ревизии остаются `pending`. Облачный receipt для новых успешно применённых
`workorder.changed` сохраняет и возвращает `workOrderVersion` из исходной транзакции.
Агент передаёт его в ACK; исходник 1С сохраняет результат вместе с `delivered`.
Старые receipts без версии не восстанавливаются по текущему заказу: агент оставляет
событие неподтверждённым для сверки. [Проверки и порядок обновления](../../docs/roadmap/notes/P-13-callback-result.md).
Преобразование ревизий и последовательная доставка пока не подключены:
Нельзя выпускать несколько ревизий с одним `baseVersion` или автоматически менять его
после конфликта. Далее нужны использование сохранённого результата, последовательная доставка головы,
разбор конфликтов, подавление эха облачных записей и сопоставление новых строк/статусов.
Облачные записи тоже попадают в журнал, с `Origin=cloud` и `CommandVersion` принятой команды.
`AcceptedCloudPayloadJSON` фиксируется до записи документа из аргумента команды,
а не из изменяемого регистра привязки; SHA-256 относится ровно к этой строке JSON.
Перед записью проверяются контракт, совпадение версии и внешний GUID, если он передан;
подписка дополнительно сверяет `workOrderId` с привязкой. Старый `BasePayloadJSON`
сохраняет прежний смысл и не выдаётся за новую команду. Временные свойства версии и JSON
восстанавливаются после успеха и исключения, включая вложенные вызовы. При неполной
паре маркеров запись отклоняется. Для `native` оба новых поля пусты.
Это provenance принятой команды, **не подтверждение доставки/проведения**.
Исторические cloud-ревизии без JSON нельзя автоматически дополнять текущим payload.
До установки добавить оба ресурса; обратное заполнение исторических ревизий не выполнять.
Немаркированные записи имеют `Origin=native`, `CommandVersion=0`; это не доказательство
ручного ввода: побочная запись другим экземпляром из обработчика тоже не имеет маркера.
Перед delivery такие побочные записи нужно сверять; автоматически считать их ручными нельзя.
Маркер устанавливается только
вокруг записи конкретного объекта и снимается/восстанавливается при успехе и исключении;
он не отключает нативные проверки и не является реквизитом HTTP-запроса.
Передача маркера через `ДополнительныеСвойства` соответствует
[рекомендации платформы для обработчиков подписок](https://1c-dn.com/library/using_global_variables_in_modules/).
Потребитель ещё не реализован и обязан не отправлять облачные ревизии обратно.
Исторические записи без `Origin` не классифицировать по догадке: оставить для сверки.
Первое создание из AvtoPult ещё не связано в момент `ПриЗаписи` и не создаёт обратную ревизию.

Writer теперь замораживает текущую проекцию до записи и сравнивает её с перечитанным
документом после возврата `Записать()`, до обновления привязки. Исключён только `externalId`,
который при создании назначается платформой. Изменение любого другого поля снимка даёт
`409 NATIVE_PROJECTION_CHANGED`; внешний обработчик откатывает документ, строки и ревизии.
Это защита от изменений поздними обработчиками, а не сравнение всех реквизитов КА2:
соглашение, подразделение и прочие отсутствующие в снимке поля пока не покрыты.
Все ревизии по-прежнему `pending`: совпадение в подписке не подтверждает итог транзакции
и не разрешает автоматически подавлять «эхо» или сдвигать baseline.
На копии дополнительно проверить позднюю смену статуса, валюты и вида цены,
полный rollback с неизменной привязкой, обычное создание и повтор терминального ответа.

## Приёмка на копии — не выполнена

1. Записать несвязанный заказ: нет ревизии. Изменить связанный: одна новая ревизия.
2. Две последовательные записи: обе сохранены с родителем и разными `Sequence`.
3. Удалить/добавить строку, изменить количество/цену: сохранить точный состав без догадок об ID.
4. Внешняя транзакция с последующим откатом: откатились документ, ревизия и голова.
5. Ошибка проведения после `ПриЗаписи`: нет зафиксированной ревизии отменённого изменения.
6. Конкурентные записи и повреждённая голова: нет потери/перезаписи ревизий.
7. Перезапуск 1С/агента: `pending` сохранены; пока нет преобразователя, HTTP-события не выдаются.
8. Облачная запись: `Origin=cloud`, версия команды записана. Следующая ручная запись того же
   объекта: `Origin=native`. Исключение нативного обработчика также не оставляет маркер.
9. Вложенный вызов восстанавливает прежний маркер; некорректная версия отклоняется до записи.
10. Две облачные команды: каждая ревизия содержит JSON именно своей версии. Изменение
    привязки после записи не меняет JSON/хеш старой ревизии. Несовпадение версии/ID,
    одиночный маркер и ошибка записи не оставляют ни ревизии, ни временных свойств.

Структурные source-contract тесты покрывают передачу/сохранение/восстановление маркеров;
они не исполняют BSL. Точная версия нативного снимка, проекция receipt и последовательный
потребитель остаются незавершёнными; данный срез их не подменяет.
